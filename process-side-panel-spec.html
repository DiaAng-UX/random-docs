Product & design spec

Process Side Panel

Node settings in the process editor · prototype behavior

A right-hand panel for editing a node's settings without leaving the canvas. It stays out of the way, keeps the diagram in view, and saves as you go — so configuring a step feels like a quick edit, not a context switch.

1 Panel behavior

Opening

  • The panel opens when you select a node on the canvas to edit it.
  • If someone else is already editing that node, we confirm before opening — so two people don't unknowingly work on the same step.
  • The open panel is part of the page's address, so a shared or refreshed link reopens the same node with its panel already showing.

Switching between nodes

  • While the panel is open, clicking a different node swaps its contents in place — the panel doesn't flash closed and reopen.
  • The header and settings update instantly to match the newly selected node.

Closing

The panel closes when you:

  • Click the ✕ in the header, or
  • Click an empty part of the canvas (deselecting the node).

Closing also clears the node selection, so the canvas returns to a clean, nothing-selected state.

2 Header

The header is the same in every settings panel — the process side panel, the data model's attribute panel, the UI designer, and any panel added later. Only its icon and title change.

On the left

  • An icon that reflects what you're editing — the node type (task, event, gateway…) in the process editor, an attribute in the data model, a UI element in the UI designer — so you always know what you're configuring at a glance.
  • A title naming the thing being configured. In the data model and UI‑designer panels this still reads <what it is> Settings — “Attribute Settings”, “Data Type Settings”. The process side panel titles by the exact node type instead — “User Task”, “Start Timer Event”, “Exclusive Gateway”, “Timer (interrupting)” — with no “Settings” suffix.
  • Long titles truncate rather than wrap or push the buttons out of reach — the header stays a single line.
Open topic — should this generalize? Right now the process panel is the odd one out: it names the exact node type, the other two panels still say “<thing> Settings”. Worth deciding whether “Settings” should come off everywhere for consistency, or whether the process panel is the exception because a node's type is more informative than “Node”.

On the right

  • A “More” button — three dots stacked vertically — holding the actions that belong to the whole thing you're editing — rather than to one field inside it. Clicking it drops a small menu open beneath it.
  • A close (✕) button, always last so it sits in the same corner everywhere.
  • Both are 24px targets with a light grey hover, spaced 8px apart.

What goes in the More menu

  • Whole-item actions only — in the data model's attribute panel that's View references and Delete; an entity gets its own longer set.
  • Destructive items sit last and read as destructive (Delete is styled in red).
  • Items the user has no rights for are left out entirely; items blocked by a read-only state are shown but disabled, so the menu still tells you what the panel can do.
  • A surface with nothing to put in the menu simply doesn't render the button at all — no empty menu.

Below the header — tabs or straight to content

  • No tabs: when a node's settings are a single group, the panel skips tabs entirely and drops straight into that group's heading right under the header — e.g. an Embedded Subprocess goes straight to General Config.
  • Tabs: when a node has more than one top-level grouping, a tab strip sits directly under the header, above any content — e.g. a User Task shows Actions and Node Config as tabs.
  • The active tab is blue with a blue underline; inactive tabs are plain grey text — no icons, no counters.
  • Whether a node type has tabs — and which ones — is fixed by what that node type needs, not a per-instance choice: two nodes of the same type always show the same tab set (or the same no-tabs layout).

3 Saving — automatic, no Save button

There's no Save button. Changes persist as you make them, and one small circle in the editor's top toolbar — sitting with the undo/redo, language and theme controls, just left of Start Process — is the single place that tells you where things stand.

It is deliberately not inside the panel header: one circle covers the whole editor, so it stays put while you open, switch and close panels, it's always visible, and it can never be covered by the full-width Warnings bar along the bottom.

The three states

StateWhat the circle shows
resting Dashed circle while something is still unsaved; a green check once everything is in
saving Spinner, turning continuously
saved Green check that pops as it lands

Save status animation

  • When a save lands, the check springs in: it starts small and faint, overshoots slightly past full size, then settles.
  • 0.6s, easing out — scale 0.7 → 1.25 → 1, fading up from 40% to full opacity.

Timing

RuleSpec
Minimum time “Saving…” is shown500ms — even when the save returns instantly
How long “Saved” lingers2s, then back to resting
Pop duration0.6s, ease-out
  • A new edit mid-cycle restarts the sequence rather than queuing up a backlog of cues.
  • While the circle is doing its job we don't also fire success toasts — one clear signal, not two.
Why save automatically?

Node config is a lot of small, frequent edits. A save-as-you-go model with a calm status cue removes the “did that stick?” doubt without making people hunt for a button.

4 Panel Categories

Settings are organized into categories — for example Properties, Event Handlers, Datasource, Validators, Conditions, Permissions. Each category is a small self-contained block:

  • A header row (42px tall when collapsed, with 12px of padding above and below the label so it sits centered in the row) with the category name on the left and its controls on the right.
  • Its items below, each as a card, stacked with even spacing.

Header states

Every category header comes in a small, fixed set of states, so they all behave identically:

StateRight-side control
CollapsedCaret pointing down — click the row to expand
ExpandedCaret pointing up — click to collapse
Collapsed / Expanded + addA “+” sits to the left of the caret, for categories you can add items to

Grouping sub-labels

  • Inside a category, related items can sit under a quiet grouping label (e.g. “Grouping”, “Static Sources”, “Hide Rules”).
  • It's deliberately smaller and lighter than a category name — a whisper, not a heading — so it organizes without competing.

5 Config cards

The config card is the repeating building block of every panel — actions, rules, streams, validators, permissions, expressions all render as one. It comes in two sizes, Card XS and Card S, which serve different content densities and interaction models and should not be used interchangeably.

Card XS 34px

Card S 50px

Redlines & specs (both cards)

Used for

  • Actions (Process Designer)
  • Event handlers
  • Validators
  • Data source options

Layout

  • Compact row: optional reorder handle, optional leading icon, title, trailing actions (add / delete), optional expand/collapse chevron.
  • Single line of text — some can carry small details inline.

Behavior

  • Trigger: clicking anywhere on the row opens the item for editing — the whole row is the target, not a dedicated edit icon.
  • Destination: opens in a side panel, with Cancel and Save at the panel level (not per row).
  • Parent / child (Actions only): a parent action row can expand/collapse to reveal its child actions inline, using the Expanded variant. Editing still happens via the side panel for each individual row (parent or child) — expanding only reveals the nested rows, it isn't an edit action.
  • Reordering & removing: items can be dragged to reorder them via the grip handle (where order matters, like actions); each card carries its own delete control, shown on the card in edit mode.

Used for

  • Expressions
  • Permissions

Layout

  • Larger card than XS (greater height, same visual standard).
  • Contains a title and a preview / summary of the configuration detail (e.g. the first few words of the condition/expression) shown directly on the card.
  • No reorder handle, no parent/child nesting.

Behavior

  • Trigger: clicking the card opens it for editing.
  • Destination: usually opens a testing modal — but not always (some configs open straight into an edit view, with no test step).
  • Summary content: always show a short, legible preview of the underlying condition/expression on the card face itself.
Why the on-card preview?

People open the card regardless, but a legible preview lets them scan and recognize items at a glance — without opening each one just to remember what it holds.

6 Adding a new item

The add control

  • Every category adds new items the same way: a “+” button in the category header, aligned to the right edge of the cards below it.
  • The “+” only appears when you're in edit mode — it's hidden when you're just viewing.
  • A newly added item appears as a new card at the bottom of that category's list, ready to configure. If the list is longer than the visible area, the panel auto-scrolls to bring the new card into view.

When a category is empty

  • Instead of a bare “+”, the category shows the DS empty state: a small dashed-circle icon, a bold “No {items} yet” title, and a one-line caption saying what those items do — centered in a thin bordered box.
  • In edit mode, a secondary “Add {item}” button sits below the caption; in a read-only view the box is the same but the button is left out, matching how add controls are hidden (not disabled) elsewhere.
  • Once the first item exists, the empty state is replaced by the list, and the header “+” takes over for adding more.

Visual example

Redlines & specs
Why “+” in the header: keeping the add affordance in one predictable spot — top-right of each category — means people never hunt for how to add something. The pattern reads identically whether they're adding an action, a rule, a stream, or a validator.

7 Action overlay

Visual example

  • size & padding
  • gap between items
Redlines & specs

Clicking an action in the list opens its full configuration in a floating card beside the panel — the action list stays visible in the panel, and the card opens just to its left.

  • The card has its own header (the action's name + a close ✕) and a scrollable body holding the action's settings.
  • It's a raised surface — rounded corners and a soft drop shadow — so it clearly floats above the canvas and panel.
  • Its width matches the side panel's default — 300px — so the pair reads as two panels of equal weight rather than a big panel with a narrow flyout tacked on. The other floating cards beside a 300px panel (the data-stream overlay, the UI‑designer's equivalent overlay) share the same 300px width for the same reason.

Opening — aligned to its trigger

  • The overlay's top edge aligns with the top edge of the action card that opened it, so it reads as attached to that row rather than floating anywhere on screen.
  • If aligning to the trigger would push the overlay past the bottom of the visible area — because the trigger sits low in a long list — the overlay instead anchors to the bottom of the panel, and its body becomes scrollable so the rest of its content stays reachable.

Saving — explicit, unlike the panel

  • The main panel autosaves, but the overlay does not. It has an explicit Save in a bar pinned to the bottom of the card, alongside Cancel.
  • Save commits the changes and closes the overlay in one step. If a required field is empty, it doesn't close — it jumps to and highlights the first problem field instead.
  • Cancel closes the overlay and discards the edits.
Why explicit here?

An action is a deeper, more deliberate edit than a quick field tweak. A clear Save / Cancel gives people a definite “commit” moment and an easy way out — while the lightweight panel around it keeps autosaving.

Unsaved changes — gently blocking, no modal

  • While the overlay has unsaved edits, it holds its ground: clicking a different action, clicking outside the card, or selecting another node on the canvas won't switch away — the panel underneath stays put.
  • Instead of interrupting with a “discard changes?” dialog, the card draws attention to itself: a red “Unsaved changes for this action” notice appears in the save bar, and the bar does a brief left-right jiggle (about 0.6s, settling as it goes) to point you at Save / Cancel.
  • Each further blocked attempt replays the jiggle, so the nudge is always fresh.
  • Only real edits count — simply opening an action or letting it load never marks it as unsaved.
Why a nudge instead of a dialog?

A confirmation modal on every stray click gets tiring fast. Pinning the panel and animating the save bar makes the unsaved state obvious and keeps the decision — save or cancel — right where the user's attention already is.
